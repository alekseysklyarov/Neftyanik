# Подготовка обновления dachahub.com.ua

Целевая схема подтверждена владельцем: Debian/Ubuntu, Docker Compose, SQL Server и Caddy. Этот документ описывает подготовку; подключение к серверу, публикация и включение таймера ещё не выполнялись.

## Что подготовлено в этой версии

- Публичные страницы подключения и стоимости, галереи и отдельное демо с 30-минутными сессиями.
- Заявки на подключение и очередь уведомлений. Отправку почты владелец отложил: в production Compose она выключена по умолчанию.
- В Compose добавлены параметры AllowedHosts и необязательной отправки почты через переменные окружения.
- Опциональный systemd-таймер ежедневного резервного копирования. Он не устанавливается и не включается при обычном обновлении сайта.

## Настройки существующего сервера

Не заменяйте действующий `deploy/.env` шаблоном целиком: сохраните пароль SQL Server и имя рабочей базы. Добавьте следующие параметры к существующим значениям:

```dotenv
SITE_ADDRESS=dachahub.com.ua
REQUIRE_HTTPS=true
ALLOWED_HOSTS='dachahub.com.ua;localhost;127.0.0.1'
SALES_NOTIFICATIONS_ENABLED=false
SALES_INBOX_URL=https://dachahub.com.ua/Platform/Requests
```

Если сервер обслуживает дополнительные имена, включите их в AllowedHosts и адреса Caddy согласно действующей конфигурации. Список AllowedHosts содержит имена без схемы и пути. Кавычки вокруг списка нужны, поскольку `.env` читается и Docker Compose, и Bash-скриптами.

Пароль Gmail на этом этапе не требуется. В `.env` не должно быть пробных паролей из `.env.example`. Не публикуйте `.env` и вывод полностью раскрытой конфигурации с секретами.

## Обновление

1. Подготовить согласованный коммит с изменениями портала. Перед публикацией проверить, что в коммит не попали журналы, файлы TestResults и посторонние локальные изменения. В текущем checkout изменения пока не закоммичены.
2. Обновить настройки `.env` на сервере, сохранив существующие секреты.
3. Для действующего сайта согласовать время обновления: скрипт ненадолго останавливает web на время миграции.
4. Запустить существующий workflow **Deploy production** для согласованного коммита master или штатный скрипт `deploy/scripts/deploy-production.sh <commit-sha>` по SSH. Workflow сам запускает существующие тесты перед публикацией.
5. Скрипт создаёт и проверяет SQL-копию, применяет миграции через отдельный контейнер и запускает новую версию. В этой версии есть миграции `AddDemoRequests` и `AddSalesRequestNotifications`; их нужно доставить вместе с кодом. При отмене запуска после миграции нельзя просто удалить новые таблицы или данные: восстановление и откат версии планируются отдельно.
6. После обновления проверить HTTPS, вход в своё товарищество, новые публичные страницы, демо и кабинет заявок. Это инструкция для публикации; такие проверки на сервере пока не выполнены.

В существующей схеме приложение использует SQL-логин `sa`. Перед коммерческим запуском требуется отдельный логин приложения с необходимыми правами на рабочую базу; административный доступ оставить операциям миграции и резервного копирования. Его создание требует настройки действующей базы, здесь она не выполнялась.

## Ежедневные копии: подготовленный пример

Файлы: `deploy/systemd/neftyanik-backup.service` и `.timer`. Пример рассчитан на `/opt/Neftyanik` и ежедневный запуск в 02:30 UTC с задержкой до пяти минут. Расписание можно изменить до установки. Это технический пример, а не утверждённое условие тарифа.

При включении на сервере администратором:

```sh
sudo install -m 644 deploy/systemd/neftyanik-backup.service /etc/systemd/system/
sudo install -m 644 deploy/systemd/neftyanik-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now neftyanik-backup.timer
```

Таймер использует существующий скрипт `create-sql-backup.sh` и ту же блокировку, что публикация: резервное копирование и миграция не должны идти одновременно. Выполняются BACKUP WITH CHECKSUM и RESTORE VERIFYONLY. Проверка файла не заменяет пробное восстановление в отдельную базу.

Копии сохраняются в `deploy/backups/sqlserver`. Автоматического удаления старых копий нет: срок хранения и контроль свободного места нужно определить отдельно. Для защиты при потере сервера нужно настроить отдельное хранилище вне этого сервера и сохранение ключей Data Protection. Его адрес и доступ ещё не определены; копирование туда не настроено. Нужен пробный цикл восстановления в отдельную базу до обещания конкретных сроков восстановления клиентам.

Docker на рабочем компьютере не найден; контейнерная сборка и запуск не выполнялись. Установка пакетов, публикация, удаление данных и изменение учётных записей сервера не производились.
