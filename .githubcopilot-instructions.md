# Project completion requirements

## Mandatory validation

A task is not complete until all required validation commands succeed.

After making code changes:

1. Build the complete solution.
2. If the build fails, inspect the errors, fix them, and build again.
3. Run the relevant automated tests.
4. If tests fail because of the changes, fix the implementation and rerun them.
5. Review the final Git diff for accidental, unrelated, duplicate, or incomplete changes.
6. Do not report the task as completed while the build or required tests are failing.

Use these commands from the repository root:

```powershell
dotnet restore
dotnet build Neftyanik.Portal.sln --no-restore
dotnet test Neftyanik.Portal.sln --no-build
```

When only part of the solution supports `dotnet` CLI, use MSBuild or the appropriate project-specific command instead.

## Failure handling

If validation cannot be completed:

* Do not claim that the implementation is finished.
* Clearly identify the failing command.
* Include the relevant error.
* Explain what remains unresolved.
* Do not hide, suppress, or work around compiler errors merely to make validation appear successful.

## Change discipline

* Make only changes required for the current task.
* Do not remove existing functionality unless explicitly requested.
* Do not introduce placeholder implementations, empty handlers, fake data, or commented-out code as a final solution.
* Do not disable tests, analyzers, nullable checks, or compiler warnings to bypass a failure.
* Preserve the existing architecture and coding conventions.
* Check all modified files before finishing.

## Final response format

At the end, report:

* Changed files
* Implemented behavior
* Build command and result
* Test command and result
* Any remaining limitations

Never use “Done”, “Completed”, or equivalent wording unless the mandatory validation has succeeded.
